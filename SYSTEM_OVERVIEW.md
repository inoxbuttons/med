# Система ИИ-ассистента для записи в клинику — описание и планы интеграции

---

## 1. Как работает система

### Общий принцип

Пациент открывает виджет «Записаться с ИИ ассистентом» на сайте клиники и ведёт диалог на естественном русском языке — так же, как в обычном мессенджере. Система понимает текст, разбирается в контексте и самостоятельно выполняет все шаги записи: находит врача, проверяет расписание, предлагает время, получает подтверждение и создаёт запись.

Никаких форм, выпадающих списков и шагов-шагов. Пациент просто пишет: *«Запишите меня к терапевту на пятницу»* — и получает конкретные варианты.

---

### Из чего состоит система

**Три уровня:**

1. **База данных** — хранит всё, что связано с клиникой: врачей, их расписания, клиники сети, услуги, приёмы (записи), пациентов. Данные постоянные, не теряются при перезапуске.

2. **Бэкенд (сервер)** — «мозг» системы. Получает сообщение от пациента, передаёт его языковой модели, выполняет действия (найти врача, проверить слоты, создать запись), формирует ответ. Всё происходит на сервере клиники, данные никуда не уходят.

3. **Виджет (чат на сайте)** — лёгкий интерфейс в браузере пациента. Отображает переписку, показывает кнопки-подсказки (например, «Подтверждаю» / «Нет»), не хранит данных.

---

### Как проходит запись

#### Шаг 1 — Пациент пишет запрос
Пациент открывает чат и описывает свою потребность любыми словами:
- *«У меня болит спина, к кому записаться?»*
- *«Хочу к Нестеровой, есть ли она в четверг?»*
- *«Запишите меня на УЗИ брюшной полости в любой день»*

#### Шаг 2 — Языковая модель понимает запрос
Сообщение поступает к языковой модели (GigaChat). Модель не придумывает данные — она умеет вызывать конкретные инструменты: «найти врача», «показать расписание», «создать запись». Результат каждого инструмента возвращается в диалог, и модель составляет ответ на его основе.

#### Шаг 3 — Поиск и уточнение
Система ищет врача по специальности или фамилии, проверяет, в каких клиниках сети он ведёт приём, и рассчитывает свободные слоты с учётом рабочего графика, перерывов и дней-исключений. Если пациент сказал «в пятницу» — сервер сам находит ближайшую пятницу, пациенту не нужно вводить дату.

#### Шаг 4 — Подтверждение
Перед созданием записи система обязательно показывает итог: кто, когда, где — и спрашивает подтверждение. Запись создаётся только после явного «да» пациента. Это защита от случайных нажатий.

#### Шаг 5 — Запись создана
Приём появляется в базе данных со статусом «запланирован» и источником «AI». Пациент получает подтверждение в чате.

---

### Дополнительные сценарии

| Что хочет пациент | Что делает система |
|---|---|
| Посмотреть свои записи | Показывает список предстоящих приёмов |
| Перенести запись | Находит существующую запись, предлагает новое время, переносит после подтверждения |
| Отменить запись | Находит запись, уточняет, отменяет после подтверждения |
| Описывает симптомы | Объясняет возможные причины, предлагает нужного специалиста, спрашивает «Записать вас?» |
| Пытается записаться на занятое время | Сообщает о конфликте, предлагает выбор: оставить обе записи или заменить |

---

### Сессия и идентификация пациента

Каждый сеанс чата имеет уникальный идентификатор (session ID), который хранится в браузере пациента в куки. Если пациент авторизован на сайте, к сессии добавляется его patient ID — тогда система может показать его записи, а не чужие. Без авторизации запись тоже возможна, но история приёмов недоступна.

История диалога хранится в памяти сервера 30 минут. Этого достаточно для завершения одного сценария.

---

### Безопасность и ограничения

- Система отвечает **только** на вопросы о записях, расписании, врачах и симптомах. На посторонние вопросы вежливо отказывает.
- Все ID врачей и клиник берутся **только из базы данных** — языковая модель не может «придумать» несуществующего врача.
- Запись, перенос и отмена выполняются **только после явного подтверждения** пациента.
- Языковая модель работает на серверах Сбера (GigaChat), данные о пациенте в запросы к модели не включаются — туда уходят только результаты поиска (имена врачей, даты, клиники).

## 2. Интеграция с МИС Инфоклиника

### Текущее состояние

Сейчас база данных системы — собственная (PostgreSQL). В ней хранятся врачи, расписания, записи и пациенты. Данные вносятся вручную или через SQL-скрипты.

### Цель интеграции

Сделать так, чтобы:
- источником правды о врачах, расписаниях и пациентах стала МИС Инфоклиника;
- записи, созданные через ИИ-ассистент, мгновенно появлялись в МИС и были видны регистраторам;
- изменения в МИС (отмена, перенос, новый врач) отражались в ИИ-ассистенте.

### Как будет устроена интеграция

**Вариант А — через API МИС (предпочтительный)**

Инфоклиника предоставляет REST API или веб-сервисы (как правило, SOAP или REST). Сервер ИИ-ассистента подключается к этому API напрямую и:

1. **Получает справочники** (врачи, специальности, клиники, услуги) — заменяет данные из своей базы данными МИС. Синхронизация по расписанию (например, раз в час) или по событию (вебхук из МИС).

2. **Получает расписание и слоты** — вместо расчёта свободного времени по собственной таблице `doctor_working_hours`, запрашивает у МИС актуальный список свободных слотов. Это исключает рассинхронизацию: если регистратор только что занял слот по телефону, ИИ уже не предложит его.

3. **Создаёт запись** — вызов API МИС `createAppointment` при подтверждении пациентом. Запись сразу появляется в журнале МИС.

4. **Отменяет / переносит** — аналогично через API МИС.

5. **Идентифицирует пациента** — при наличии patient ID запрашивает у МИС карту пациента и его будущие приёмы.

**Что нужно от Инфоклиники:**
- Документация на API (методы, авторизация, форматы)
- Тестовый стенд с доступом
- Учётные данные (токен или логин/пароль для API-пользователя)

---

**Вариант Б — прямое подключение к базе данных МИС**

Инфоклиника работает на MS SQL Server (или другой СУБД). Если администратор МИС предоставляет доступ к базе данных, ИИ-ассистент может работать с ней напрямую — без API.

**Что читается из базы МИС:**
- Справочники: врачи, специальности, клиники, услуги, их связи и цены
- Рабочие графики врачей: дни приёма, часы работы, длительность слота, перерывы
- Исключения: отпуска, больничные, нерабочие дни
- Существующие записи на приём (для расчёта занятых слотов)
- Карточки пациентов (для идентификации по номеру телефона или ID)

**Что записывается в базу МИС:**
- Новые записи на приём — напрямую в таблицу записей МИС, с указанием источника «AI»
- Отмены и переносы — обновление статуса записи в той же таблице

**Преимущества:**
- Данные всегда актуальны — нет задержки синхронизации
- Не нужен API, достаточно read/write доступа к нескольким таблицам
- Регистраторы в МИС мгновенно видят записи от ИИ-ассистента

**Риски и ограничения:**
- Требуется схема базы данных МИС и понимание структуры таблиц
- Прямая запись в БД стороннего продукта — без гарантий со стороны вендора; при обновлении МИС структура таблиц может измениться
- Необходим отдельный пользователь БД с минимально необходимыми правами (SELECT на справочники и расписания; INSERT/UPDATE только в таблицу записей)
- Рекомендуется тестирование на копии базы перед запуском в prod

**Что нужно от клиники:**
- Схема (DDL) ключевых таблиц МИС: врачи, расписания, записи, пациенты
- Хост и порт сервера БД (или VPN-доступ)
- Учётная запись с нужными правами
- Контакт технического специалиста Инфоклиники для уточнения бизнес-логики полей

**Как это выглядит на практике:**

Сервер ИИ-ассистента устанавливает соединение с БД Инфоклиники (через JDBC/ODBC или нативный драйвер MS SQL). При запросе пациента «покажи врачей-терапевтов» система выполняет SELECT напрямую к таблицам МИС. При подтверждении записи — INSERT в таблицу приёмов МИС. Никакой промежуточной базы не нужно.

---

**Вариант В — через файловую синхронизацию (резервный)**

Если ни API, ни прямой доступ к базе недоступен:

- МИС экспортирует данные (расписания, записи) в файлы (CSV/XML) по расписанию — раз в 5–15 минут.
- Сервер ИИ-ассистента читает эти файлы и обновляет свою базу.
- Новые записи от ИИ записываются в промежуточную таблицу или файл, откуда МИС забирает их.

Этот вариант наименее предпочтителен: данные могут устареть на время между выгрузками, требует настройки со стороны МИС.

---

### Что меняется в коде при интеграции

Вся бизнес-логика — инструменты поиска врачей, расчёта слотов, создания записей — сконцентрирована в одном модуле (`booking.service`). Для интеграции с МИС:

- Текущие методы работы с базой данных заменяются на вызовы API Инфоклиники (или промежуточного слоя).
- Остальная система (ИИ-модель, логика диалога, виджет) не меняется.
- Параллельно можно оставить локальную базу как резерв на случай недоступности МИС.

---

### Этапы интеграции (общие для всех вариантов)

| Этап | Содержание |
|---|---|
| 1. Выбор варианта | Определить, что доступно: API / прямой доступ к БД / файловый экспорт |
| 2. Схема данных | Получить структуру таблиц МИС или описание API, составить маппинг полей |
| 3. Доступ | Получить учётные данные (API-ключ или пользователь БД), настроить сеть |
| 4. Справочники | Подключить врачей, клиники, специальности, услуги из МИС |
| 5. Расписание и слоты | Получать занятость из МИС вместо собственного расчёта |
| 6. Создание записей | Записи от ИИ попадают напрямую в МИС |
| 7. Пациенты | Связать авторизацию на сайте с карточкой в МИС |
| 8. Тест на копии | Проверка на тестовом стенде МИС, без риска для данных |
| 9. Пилот | Запуск в одной клинике сети, мониторинг |
| 10. Масштаб | Подключение остальных клиник сети |

## 3. Интеграция с сайтом клиники

### Текущий подход (прототип)

Сейчас виджет встроен в отдельные HTML-страницы (`index.html`, `index1.html`) — это демо-версия. Реальный сайт клиники работает на другой платформе (CMS или собственная разработка).

### Как будет выглядеть интеграция

**Шаг 1 — PHP-включение (уже подготовлено)**

Страницы `index.html` / `index1.html` предназначены для рендера через PHP (`index.php`). PHP перед отдачей страницы:
- Проверяет сессию пациента (авторизован или нет)
- Вставляет в HTML переменные: `PHP_SESSION_ID`, `PHP_CLIENT_ID`, `PHP_CLINIC_NET_ID`
- JavaScript на странице читает эти переменные и передаёт их в iframe чата

Таким образом авторизованный пациент сразу получает персонализированный чат — без лишнего логина.

**Шаг 2 — Виджет как подключаемый скрипт**

Для встройки в любую страницу существующего сайта (на любой CMS — WordPress, Bitrix, собственная) предусмотрен вариант подключения одним тегом:

```html
<script src="https://med.clinic/widget.js"
        data-session="<?= $sessionId ?>"
        data-client="<?= $clientId ?>"
        data-clinic-net="1">
</script>
```

Скрипт сам создаёт кнопку «Записаться с ИИ ассистентом» и всплывающее окно чата. Сайту не нужно знать о внутреннем устройстве системы.

**Шаг 3 — Авторизация пациента**

Пациент авторизуется через личный кабинет сайта клиники (существующий механизм). При входе PHP-сессия получает ID пациента. Этот ID передаётся в виджет — чат становится персонализированным (пациент видит свои записи, не нужно называть имя).

Неавторизованные пользователи также могут пользоваться чатом — они могут записаться, но история приёмов недоступна.

**Шаг 4 — Мобильная версия**

Виджет уже адаптирован: на телефоне чат открывается на весь экран, кнопка видна выше основного баннера. Дополнительной адаптации не требуется.

---

### Где размещается сервер

Бэкенд (сервер ИИ-ассистента) разворачивается:
- На сервере клиники (рекомендуется — данные пациентов не покидают инфраструктуру)
- Или на отдельном VPS в той же сети

Сайт обращается к бэкенду через внутреннюю сеть или защищённый HTTPS-эндпоинт. Виджет в браузере пациента делает запросы только на этот сервер.

---

### Схема взаимодействия (итог)

```
Сайт клиники (любая CMS)
  └─ PHP: авторизация пациента → session_id, client_id, clinic_net_id
       └─ HTML-страница с виджетом чата
            └─ iframe / JS-виджет → chat.html
                 └─ HTTPS POST /chat/message (бэкенд)
                      ├─ GigaChat (понимание текста, выбор действий)
                      └─ МИС Инфоклиника API
                           ├─ Врачи, расписания, слоты
                           └─ Создание / отмена / перенос записей
```
