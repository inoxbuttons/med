# 1. Текущая архитектура: анализ

Дата анализа: 2026-11-17. Ветка `21vek`.

## 1.1 Как устроен ход диалога сейчас

```
widget / telegram / max
        │  POST /api/chat/message {sessionId, message, clinicNetId, misType?}
        ▼
ChatService.sendMessage (chat.service.ts, 1256 строк)
  ├─ regex-фильтры: инъекции, экстренные симптомы, «симптомное» сообщение
  ├─ pendingConfirmation / pendingConflict — regex по «да/нет/заменить»
  ├─ systemPrompt (system-prompt.txt, ~10.7 КБ)
  │    + дата + куски для MedFlex (гость, записи сессии, конфликт)
  ├─ tools = BookingService.getTools(misType)   ← 13 схем (local) / 9 (medflex)
  └─ runToolLoop: до 6 итераций
        LLM(system + ВСЯ история + tools) → tool_call → BookingService.executeTool
          ├─ LocalDbService   (1633 строки: схемы инструментов + SQL + бизнес-логика)
          ├─ MedflexService   (1149 строк: свои схемы + клиент + бизнес-логика)
          └─ InfoclinicaService (схемы local, своя реализация)
        результат инструмента → в историю → снова LLM …
```

Вся логика сценария (первичный/повторный, направление, заявка оператору,
перенос, отмена, цены) описана **текстом в промпте**, и её исполняет модель.
Код пытается её «подстраховать» десятками проверок на `toolName === …` и
`misType === 'medflex'` в `runToolLoop`.

## 1.2 Откуда берутся входные токены (замер по `token_usage`)

| Показатель | Значение |
|---|---|
| «Привет» — один вызов без инструментов | **5 442** входных токена |
| Медиана на вызов Qwen | 5 641 |
| Максимум на вызов | 14 298 |
| Средний выход | 271 |
| Сценарий «УЗИ → ближайшее время» (2 сообщения) | 4 вызова, 22 196 токенов |
| Длинный сценарий (probe-nd) | 15 вызовов, 169 437 токенов |

Доля входных токенов в счёте — **~96 %**. Три причины, по убыванию веса:

1. **Фиксированная надбавка ~5,4 тыс. токенов на каждый вызов.**
   Системный промпт (~2,5 тыс.) + JSON-схемы 13 инструментов (10,8 тыс.
   символов, ~3 тыс. токенов) уходят в модель при каждом вызове, даже на
   «Привет».
2. **Несколько вызовов на одно сообщение пациента.** Модель вызывает
   один инструмент за раз; каждый вызов — повторная отправка
   промпта + схем + всей истории. Типичная запись: 2–4 вызова на ход,
   итого 8–15 вызовов на запись.
3. **Растущая история.** Результаты инструментов (списки из 30 услуг,
   слоты по дням, врачи с клиниками) лежат в истории и пересылаются в
   каждом следующем вызове. Компактизация срабатывает только после
   успешной записи.

Вывод: сокращение промпта даст проценты. Порядок величины меняется только
если **убрать из модели схемы инструментов, перебор инструментов и
историю с сырыми данными**.

## 1.3 Почему систему трудно расширять

| Проблема | Где видно |
|---|---|
| Сценарий записи живёт в промпте, а не в коде | `system-prompt.txt`: шаги 1–7, flow направлений, перенос, цены |
| Промпт знает форматы конкретной МИС | `dtSlot.dt_start`, `uuid`, `specialityId`, `allSlots` — это поля MedFlex |
| Ядро знает про конкретные МИС | `chat.service.ts`: ветки `misType === 'medflex'` в подтверждении, конфликте, гостевом режиме, компакте |
| Каждая МИС объявляет свои инструменты | `LocalDbService.getTools()` и `MedflexService.getTools()` — разные наборы и описания; модель видит разный API в зависимости от клиента |
| Адаптер = схемы + SQL + бизнес-правила в одном файле | `local-db.service.ts` 1633 строки, `medflex.service.ts` 1149 |
| Настройки клиники разбросаны | `clinic_nets` (mis, ключи), неиспользуемая `clinic_net_configs`, `CHAT_SYSTEM_PROMPT` в env (один на всех) |
| Особенности сети решаются данными «под модель» | для 21vek: аббревиатуры УЗИ/МРТ/КТ в коде поиска, правки названий кнопок в `stand.js` |
| Поиск услуг — ILIKE по словам | синонимы и жаргон («ФГДС», «кукушка») ловит только модель, перебирая запросы |
| Регрессии ловятся только живыми прогонами модели | `tests/cycle*.ts` ходят в LLM — каждый прогон стоит денег |

## 1.4 Что уже хорошо и стоит сохранить

- Серверное исполнение подтверждения (`pendingConfirmation`) — модель не
  может «записать» без явного «да».
- Экстренные симптомы ловятся сервером до модели.
- Расчёт слотов, конфликты, атомарный перенос — уже в коде, не в модели.
- Учёт токенов в `token_usage` — основа для измерения эффекта.
- Фильтр по `clinicNetId` во всех запросах к локальной БД (доделан в этой ветке).
- pgvector уже установлен в БД (`CREATE EXTENSION vector`), но не используется.
