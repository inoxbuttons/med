# 2. Целевая архитектура: жёсткий пайплайн + гибридный поиск

## 2.1 Принцип

Модель перестаёт быть оркестратором. Она делает **две узкие задачи**:

1. **Понять** сообщение пациента → структурированный JSON (намерение + параметры).
2. **Сказать по-человечески** там, где шаблона недостаточно (симптомы, вопросы о клинике, непонятные реплики).

Всё остальное — выбор шага сценария, поиск, слоты, запись, подтверждения — делает
код. Модель не видит схем инструментов, сырых результатов поиска и полной истории.

```
сообщение / нажатие кнопки
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ 0. Guard (код)       инъекции, экстренные симптомы, длина     │
├─────────────────────────────────────────────────────────────┤
│ 1. Понимание                                                  │
│    кнопка с payload → интент без модели (0 токенов)           │
│    «да/нет/1/2/завтра» в ожидаемом шаге → правила (0 токенов) │
│    иначе → NLU-вызов модели: короткий промпт + состояние       │
│            диалога + реплика → JSON по схеме                   │
├─────────────────────────────────────────────────────────────┤
│ 2. Dialog Engine (код, конечный автомат по сценариям)          │
│    слоты сценария: что известно, чего не хватает               │
│    ├─ Catalog Search (гибридный RAG) — услуги, специальности,  │
│    │                                  врачи                    │
│    ├─ Booking Port → адаптер МИС (local / medflex / infoclinica)│
│    └─ Policy клиники (из профиля сети)                         │
├─────────────────────────────────────────────────────────────┤
│ 3. Ответ                                                       │
│    шаблон (списки слотов, сводка, подтверждение) + кнопки      │
│    либо генерация моделью (свободный ответ) — короткий промпт  │
└─────────────────────────────────────────────────────────────┘
```

## 2.2 Слои и границы

```
src/
  core/                      ← одинаково для всех клиник, не знает про МИС
    domain/                  Clinic, Doctor, Speciality, Service, Slot,
                             Appointment, Patient, OperatorRequest
    nlu/                     NLU-вызов, JSON-схема интентов, правила без модели
    dialog/                  движок + сценарии (flows)
    catalog/                 гибридный поиск, индекс, синхронизация
    render/                  шаблоны ответов, кнопки
    prompts/                 сборка промптов из слоёв (см. 2.5)
    ports/                   интерфейсы: BookingPort, CatalogSourcePort,
                             LlmPort, SessionStore
  adapters/
    mis/local/  mis/medflex/  mis/infoclinica/   ← реализация портов
    llm/qwen3/  llm/gigachat/  llm/openai/
  clinics/                   ← только данные, без кода ядра
    profiles/<net>.yaml       профиль сети (сид для БД, см. 2.5)
    prompts/<net>/*.md        слои промптов сети
  channels/                  web-виджет, telegram, max — тонкие обёртки
```

Правило зависимостей: `core` → только `core/ports`. Адаптеры реализуют порты.
Ветки `if (misType === 'medflex')` в ядре запрещены — разница уходит в адаптер
(формат слотов, uuid, гостевой режим как флаг возможностей адаптера).

### BookingPort (единый для всех МИС)

```ts
interface BookingPort {
  capabilities(): { guestBooking: boolean; patientAppointments: boolean;
                    reschedule: 'atomic' | 'cancel+book' | 'none'; ... };
  findSlots(q: { doctorIds?; serviceId?; clinicIds?; mode; date?; dayOfWeek?; timeOfDay? }): Promise<Slot[]>;
  book(r: BookingRequest): Promise<BookingResult>;     // conflict → {kind:'conflict', existing}
  cancel(appointmentRef: string): Promise<Result>;
  reschedule(ref: string, r: BookingRequest): Promise<BookingResult>;
  patientAppointments(patient: PatientRef): Promise<Appointment[]>;
  createOperatorRequest(r: OperatorRequestInput): Promise<Result>;
}
interface CatalogSourcePort {           // для синхронизации в индекс
  clinics(); specialities(); doctors(); services(); consultationServices(doctorId);
}
```

`Slot` — доменный тип (`start`, `end`, `doctorId`, `clinicId`, `ref`), а не `dtSlot`.
Адаптер MedFlex прячет свой формат внутри `ref`.

## 2.3 Понимание (NLU)

Один вызов модели на сообщение пациента, и только когда правила не справились.

Вход (~700–1 200 токенов):
- промпт NLU (ядро + слой клиники, см. 2.5) — ~400–600 токенов;
- **состояние диалога**, а не история: текущий сценарий, заполненные слоты,
  что спросили последним, показанные варианты (`1. Иванов 10:00 …`), 2–3
  последние реплики текстом;
- реплика пациента.

Выход — JSON по схеме (structured output / `response_format`, где провайдер умеет;
иначе JSON в тексте + валидация + 1 повтор):

```json
{
  "intent": "book_doctor | book_service | my_appointments | cancel | reschedule |
             price | clinic_info | symptoms | answer_slot | confirm | decline |
             smalltalk | other",
  "entities": {
    "speciality": "невролог", "doctorName": "Нестерова",
    "serviceQuery": "узи щитовидной", "childPatient": false,
    "clinic": "северный", "date": null, "dayOfWeek": "thu", "relative": "tomorrow",
    "time": "15:00", "timeOfDay": "morning",
    "choice": 2, "visitType": "primary", "hasReferral": true,
    "patient": { "fullName": "...", "phone": "...", "birthday": "..." }
  },
  "edit": ["dayOfWeek"]          // пациент поправил ранее заданный слот
}
```

Без модели обрабатываются (правила/регэкспы, уже частично есть):
нажатия кнопок (payload), «да/нет», номер варианта «2», «завтра/в пятницу»
в шаге выбора даты, телефон и дата рождения в шаге сбора данных.

## 2.4 Гибридный поиск по каталогу (RAG)

Цель: модель больше не перебирает `find_services("…")` в цикле, а синонимы,
жаргон и опечатки ловит поиск.

### Индекс

Таблица `catalog_index` (pgvector уже стоит):

| поле | назначение |
|---|---|
| `clinic_net_id`, `kind` (`service`/`speciality`/`doctor`/`med_field`), `entity_id` | что найдено и в какой сети |
| `title` | каноническое название |
| `search_text` | название + направление + синонимы + аббревиатуры + описание |
| `tsv tsvector` | полнотекстовый поиск, конфигурация `russian` (морфология) |
| `embedding vector(N)` | семантический поиск |
| `meta jsonb` | `selfBooking`, `atDoctorVisit`, клиники, цена — для фильтров и ответа |

Индексы: GIN по `tsv`, GIN `pg_trgm` по `title` (опечатки, фамилии в падежах),
HNSW по `embedding`.

### Запрос

```
q → три кандидата-списка (top 20 каждый, фильтр clinic_net_id + kind):
    1. FTS:      ts_rank(tsv, websearch_to_tsquery('russian', q))
    2. trigram:  similarity(title, q)              — опечатки, фамилии
    3. vector:   embedding <=> embed(q)            — смысл, жаргон
  → слияние Reciprocal Rank Fusion (k=60) → top-K (5–8)
  → решение в коде:
       явный лидер (отрыв по скору)  → берём, идём дальше
       2–8 близких                   → показываем списком с кнопками
       ничего                        → «не нашли», предлагаем специалиста
```

- **Врачи**: только trigram + FTS (эмбеддинги на фамилиях бесполезны).
  Падежи («к Нестеровой») — trigram + нормализация окончаний.
- **Специальности**: «болит спина → невролог» — вектор по описанию
  специальности + словарь симптомов из профиля клиники.
- **Синонимы сети** (УЗИ ↔ ультразвуковое, «кукушка», местные названия
  кабинетов) — в профиле клиники, попадают в `search_text` при индексации.
  Хардкод `SERVICE_ABBREVIATIONS` из `local-db.service.ts` переезжает туда.
- **Эмбеддинги**: модель с хорошим русским (bge-m3 или multilingual-e5).
  Варианты: API эмбеддингов cloud.ru, если там есть подходящая модель,
  или локальный контейнер (text-embeddings-inference). Каталог
  индексируется один раз и при изменениях; на запрос — одно встраивание
  короткой строки.
- **Источник для индекса**: для local — своя БД; для MedFlex/Инфоклиники —
  периодическая синхронизация через `CatalogSourcePort`. Поиск одинаковый
  для всех МИС.
- Опционально, при неоднозначности: короткий вызов модели для
  переранжирования 5–8 названий (~300 токенов). По умолчанию выключен.

## 2.5 Промпты по клиникам: слои

Промпт отличается от клиники к клинике, но не должен ломать ядро. Поэтому
промпт **собирается** из слоёв, а не хранится одним файлом:

```
┌───────────────────────────────────────────────┐
│ core/<task>.md   ядро: формат JSON, правила    │  меняют разработчики,
│                  безопасности, запреты          │  общий для всех
├───────────────────────────────────────────────┤
│ clinics/<net>/<task>.md  слой сети:            │  меняется под клинику
│   тон, обращение, имя ассистента, о клинике,   │
│   местные термины, правила направлений,         │
│   подсказки по специальностям/симптомам         │
├───────────────────────────────────────────────┤
│ переменные: {{clinicName}}, {{today}},          │  подставляет код
│   {{clinics}}, {{phone}}, {{dialogState}} …     │
└───────────────────────────────────────────────┘
```

Задачи (`<task>`), у каждой свой короткий промпт: `nlu`, `answer` (свободный
ответ), `symptoms`, при необходимости `rerank`. Клиника может переопределить
слой любой задачи, но не ядро. Правила, критичные для безопасности (только
подтверждённая запись, экстренные случаи, никаких диагнозов), стоят в ядре и
дублируются кодом.

Хранение:
- в репозитории — `clinics/prompts/<net>/*.md` как сид и история изменений;
- в БД — `clinic_prompt_layers (clinic_net_id, task, version, content, active)`,
  чтобы менять без релиза; кеш в памяти, перезагрузка по сигналу;
- `PromptBuilder.build(task, netId, vars)` → итоговый текст + хеш версии,
  хеш пишется в `token_usage` (видно, какой версии промпта стоил ход).

Помимо промптов, всё, что отличает клинику, лежит в **профиле сети**
(`clinic_net_profiles.settings jsonb`, сид из `clinics/profiles/<net>.yaml`):

```yaml
net: xxi-vek
mis: local                    # local | medflex | infoclinica
llm: { provider: qwen3, model: Qwen/Qwen3.5-397B-A17B }
features:
  visitTypeQuestion: true     # «первичный/повторный»
  referralFlow: operator      # operator | doctor | off
  guestBooking: true
  showPrices: on_request
patientFields: [fullName, phone, birthday]
synonyms:
  узи: [ультразвуковое исследование]
  мрт: [магнитно-резонансная томография]
symptomHints:
  спина: невролог
templates:                    # переопределение текстов шаблонов
  greeting: "Здравствуйте! Я ассистент клиник «XXI Век»…"
```

Новая клиника = профиль + слои промптов + выбор адаптера. Код ядра не меняется.

## 2.6 Dialog Engine

Подробно о том, как движок справляется с разнообразием формулировок (фрейм
«цель + ограничения», резолвер требований, обработчики вопросов, агент как
запасной путь), — в [04-dialog-model.md](04-dialog-model.md). Ниже — пример
требований цели `book` к врачу:

```
need speciality|doctor ──► search ──► (несколько) выбор врача
        ▼
need slot ──► BookingPort.findSlots ──► показать (шаблон + кнопки)
        ▼
policy.visitTypeQuestion? ──► первичный/повторный (consultation services)
        ▼
need patient data? ──► запрос ФИО/телефона/ДР
        ▼
summary + «Подтверждаете?» ──► confirm ──► BookingPort.book
                                    └──► conflict ──► заменить / оставить обе
```

Аналогично: `book_service` (self_booking → слоты услуги; иначе направление →
заявка оператору / запись к врачу), `cancel`, `reschedule`, `my_appointments`,
`price`, `symptoms` (код выбирает специальность, модель пишет текст),
`clinic_info` (модель + данные клиник из профиля).

Поправки посреди сценария («нет, лучше в четверг») — NLU возвращает `edit`,
движок сбрасывает зависимые слоты и пересчитывает шаг.

Модель видит текущий запрос: во входе NLU — накопленные `entities` в JSON (без
персональных данных) и названия клиник сети. Возвращает только изменения к нему:
новые значения в `entities`, отменённые поля в `unset` («в любое время» →
`["time"]`, «в любой клинике» → `["clinic"]`). Патч, а не весь объект: пропущенное
моделью поле не теряется молча. Клинику движок сверяет со списком клиник сети по
словам названия и адреса; не нашёл или там нет времени — говорит об этом, а не
показывает другие клиники молча. Ответ модели пишется в лог (`NLU <session>`),
персональные поля — как `***`.

Реплика модели: кроме данных, NLU может вернуть `say` — 1–2 предложения пациенту,
когда реплика не сводится к данным (вопрос не по сценарию, возражение, непонятное).
Код ставит её перед ответом шаблона, если сам ничего не пояснил; посреди записи
вопрос не по сценарию отвечается этой фразой и тем же шагом, без агента и без сброса
записи. Факты говорит только код: фраза со временем, ценой или «записала» отбрасывается
(`safeSay`).

Состояние сессии — `SessionStore` (сейчас `Map` в памяти; порт позволит
перейти на Redis/Postgres без изменения ядра, сессии не будут теряться при
рестарте).

## 2.7 Ответы и кнопки

- Структурные ответы (слоты, врачи, услуги, сводка, подтверждение, «запись
  создана») — **шаблоны без модели**. Даты в них уже формирует код
  (`dateLabel`), ошибки «модель перепутала день» исчезают.
- В ответе API появляется `quickReplies: [{label, payload}]`. Виджет и
  мессенджеры (inline-клавиатуры Telegram/MAX) показывают кнопки; нажатие
  уходит payload'ом и не требует NLU.
- Свободный текст (симптомы, «есть ли парковка», непонятная реплика) —
  вызов `answer` с коротким промптом и состоянием, без схем инструментов.

## 2.8 Ожидаемый эффект по токенам (оценка)

| | Сейчас | Цель |
|---|---|---|
| Вызовов модели на сообщение | 1–6 (медиана ~2) | 0–1 (кнопки и «да/нет» — 0) |
| Входных токенов на вызов | 5,4–14 тыс. | 0,7–1,5 тыс. |
| Запись к врачу «от начала до конца» | 40–80 тыс. | ~3–6 тыс. |

Это оценка по текущим замерам, не измерение. Реальный эффект меряем по
`token_usage` на одном и том же наборе сценариев до и после.

## 2.9 Что теряем и как компенсируем

| Риск | Компенсация |
|---|---|
| Модель хуже справляется с «нестандартными» диалогами (два намерения в одной реплике, вопросы не по сценарию) | интент `other` → свободный ответ модели + возврат в текущий шаг; сбор нерасклассифицированных реплик в лог для доработки |
| Поиск находит не то, что модель «догадалась бы» | синонимы в профиле, переранжирование моделью при неоднозначности, золотой набор запросов для регрессии |
| Больше кода сценариев | сценарии тестируются офлайн без модели (NLU замокан) — дешевле, чем сейчас |
| Переход ломает работающее | движок включается флагом на сеть (`engine: tools | pipeline`), старый путь работает параллельно до отключения |
