# 4. Модель диалога: как код справляется с разнообразием запросов

Пациенты формулируют запросы как угодно:
- «Запишите к Нестеровой на четверг в 15:00»;
- «Можно прийти сейчас с болью в животе?»;
- «Работает ли Нестерова в субботу?».

Писать отдельный сценарий на каждое сочетание нельзя: их тысячи. Поэтому код
**не перебирает сценарии**, а работает с тремя небольшими вещами.

## 4.1 Запрос = цель + ограничения

NLU превращает любую реплику в **фрейм**:

```
goal:        book | info | cancel | reschedule | my_appointments | other
subject:     doctor | speciality | service | clinic | appointment | symptom
constraints: doctor, speciality, service, clinic, date, dayOfWeek, time,
             timeOfDay, now, nearest, child, visitType, hasReferral, …
question:    (только для goal=info) schedule | price | address | hours |
             preparation | walk_in | has_service | …
```

Разнообразие формулировок ложится на **комбинации полей одного фрейма**. Число
целей и типов вопросов небольшое и почти не растёт. Растёт число вариантов,
как пациент их сочетает, но это обрабатывает один общий механизм, а не
отдельный код.

## 4.2 Резолвер: шаги не по порядку, а «чего не хватает»

Сценарий — это не линейный скрипт, а список **требований** цели. Например,
для `book`:

| Требование | Чем закрывается |
|---|---|
| кто/что (врач, специальность или услуга) | ограничения → поиск по каталогу; при симптоме — подбор специальности |
| слот | ограничения по дате, времени, клинике → `findSlots` |
| тип приёма | политика клиники (`visitTypeQuestion`) |
| данные пациента | сессия, авторизация или вопрос |
| подтверждение | «да» / кнопка |

На каждом ходу движок:
1. применяет новые ограничения к фрейму (дополнение или поправка);
2. находит **первое незакрытое требование**;
3. пытается закрыть его сам (поиск, слоты, данные сессии);
4. если сам не может — задаёт **один** вопрос или показывает варианты.

Порядок, в котором пациент сообщает данные, не важен. «К Нестеровой в четверг
в 15:00» сразу закрывает два требования, и движок переходит к проверке слота.
«Хочу к неврологу» закрывает одно, и движок спрашивает время.

## 4.3 Вопросы — это запросы к тем же данным

`goal=info` не требует сценария: нужен **обработчик вопроса**, то есть запрос к
домену плюс шаблон ответа. Обработчиков немного, порядка десяти, и каждый
переиспользует ограничения фрейма.

После ответа движок предлагает перейти к записи **с уже заполненным фреймом**
(«Записать Вас?») — диалог перетекает из вопроса в запись без потери контекста.

## 4.4 Разбор примеров

**«Запишите к Нестеровой на четверг в 15:00»**
```
goal=book, subject=doctor, constraints={doctor:"Нестерова", dayOfWeek:thu, time:"15:00"}
→ каталог: Нестерова → doctorId
→ findSlots(doctorId, четверг): 15:00 свободно?
     да  → следующее требование: тип приёма → данные → сводка
     нет → шаблон «В 15:00 занято, ближайшее в четверг: 14:30, 16:00» + кнопки
```
Один вызов NLU. Остальное делает код.

**«Можно прийти сейчас с болью в животе?»**
```
guard: проверка красных флагов (резкая боль, кровь, температура) → если есть, 103/112
goal=book (или info:walk_in), subject=symptom,
     constraints={symptom:"боль в животе", now:true}
→ симптом → специальность: подсказки профиля (живот → гастроэнтеролог, иначе терапевт)
→ findSlots(специальность, сегодня, nearest)
→ ответ: политика клиники walk_in («без записи не принимаем» / «есть дежурный терапевт»)
   + «Сегодня ближайшее: терапевт Иванова в 16:30» + кнопки
```
Текст про симптом пишет модель (задача `symptoms`, короткий промпт без
диагнозов). Специальность и слоты подбирает код.

**«Работает ли Нестерова в субботу?»**
```
goal=info, question=schedule, constraints={doctor:"Нестерова", dayOfWeek:sat}
→ обработчик schedule: часы работы + свободные слоты на ближайшую субботу
→ шаблон: «Да, Нестерова принимает в субботу с 9:00 до 15:00 на Северном.
           Свободно 22 ноября: 10:00, 11:30. Записать?» [10:00] [11:30]
→ нажатие кнопки → goal=book, фрейм уже заполнен → тип приёма → данные → подтверждение
```

**«Отмените мою запись на завтра и запишите на пятницу»** — две цели. NLU
возвращает очередь фреймов: `[cancel{date:tomorrow}, book{dayOfWeek:fri}]`.
Движок выполняет их по очереди. Врача для второй цели берёт из отменяемой
записи, если пациент его не назвал.

## 4.5 Длинный хвост: агент как запасной путь

Какие бы цели и вопросы мы ни заложили, останутся запросы, которые в них не
укладываются: «у меня направление из другой клиники, его примут?», «можно ли
перенести анализы, если я заболел», сложные цепочки условий.

Для них — **запасной путь**: `goal=other` или неуверенный NLU → агентный режим
по образцу текущего, но урезанный:
- только **читающие** инструменты (поиск по каталогу, слоты, часы работы,
  информация о клинике); записать, отменить и перенести агент не может;
- короткий промпт ответа + слой клиники, в контексте состояние, а не вся
  история;
- лимит 2–3 вызова инструментов;
- если агент понял, что пациент хочет записаться, он возвращает фрейм, и дальше
  ведёт движок.

Так дорогой режим тратится только на редкие запросы, а действия с записями
всегда идут через код с подтверждением.

## 4.6 Как не застрять: измерять и поднимать частое в движок

- В лог пишется каждый ход: фрейм, какой путь сработал (правила / NLU+движок /
  агент), токены.
- Раз в неделю смотрим частые формулировки, ушедшие в агент. Если паттерн
  повторяется — добавляем в схему NLU поле, тип вопроса или
  требование.
- Цель — 90 %+ ходов без агента. Доля агента — главная метрика
  покрытия.

## 4.7 Что из этого зависит от клиники

Цели, требования и механизм резолвера — ядро. От клиники зависят:
- политики, влияющие на требования (`visitTypeQuestion`, `referralFlow`,
  `walkIn`, обязательные поля пациента);
- подсказки «симптом → специальность», синонимы;
- тексты шаблонов и слои промптов (`nlu`, `answer`, `symptoms`, `agent`);
- набор включённых типов вопросов (например, `preparation` есть только там,
  где заполнены памятки по подготовке).

Новый тип вопроса или требование, нужные одной клинике, добавляются в ядро
один раз и включаются флагом в профиле.
