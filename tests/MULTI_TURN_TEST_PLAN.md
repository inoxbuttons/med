# Многоходовые тесты чата — план

Формат для каждого теста:

> **ID — название**
> _Цель._ Что именно проверяем.
> _Предусловия._ Состояние мока/сессии перед стартом.
> _Шаги._ user → assistant с ожиданием на каждом ходе.
> _Хард-проверки._ slot.date, function.success, конкретное поле в args/result.
> _Софт-проверки._ Что должно/не должно быть в reply.

Все тесты — отдельные сессии (`newSession('m3-A1')` …). Перед группой — `resetMock()` если затрагиваются существующие записи. Бэкенд должен поддерживать всё: normalizer дат, pendingConfirmation, pendingConflict, foldCompletedBookings, медфлекс services + speciality.

Тесты складываются в **`cycle3-multi-turn.ts`** (одним файлом) или разнести по группам — решим при реализации.

## A. Уточнение/смена параметров до записи

### A1 — Отказ от предложенного слота → другой день
_Цель._ Пациент может пере-запросить слоты, ничего не теряя.
_Шаги._
1. user: «Запиши меня к терапевту в среду»
2. assistant: показывает слоты на среду (Ивановой)
3. user: «А есть на пятницу?»
4. assistant: показывает слоты на пятницу
5. user: «Возьму первое»
6. assistant: спрашивает ФИО/телефон/ДР
7. user: даёт данные
8. assistant: сводка с **пятницей**
9. user: «Подтверждаю»
10. assistant: запись создана

_Хард._ В `assistant.function_call(find_doctors_and_slots)` после шага 3 → `dayOfWeek=пятница`. Финальная запись `book_appointment.success=true` с `startTime` на пятнице.

### A2 — Уточнение «есть утром / вечером»
_Цель._ Бот фильтрует/перезапрашивает по времени суток после первого ответа.
_Шаги._
1. user: «Запиши к терапевту во вторник»
2. assistant: показывает слоты Петрова (доступен с 10:00 до 17:30)
3. user: «А вечером есть?»
4. assistant: показывает только вечерние (≥16:00) ИЛИ переспрашивает
5. user: «Беру 17:00»
6. … полный flow до записи

_Хард._ Финальный `book_appointment.startTime` → `HH:MM ≥ 16:00`. Слот во вторник.
_Софт._ В reply шага 4 нет времён <16:00.

### A3 — Уточнение «А в 13:00 во вторник?»
_Цель._ Конкретное время после общего запроса.
_Шаги._
1. user: «Запиши к терапевту во вторник»
2. assistant: общий список
3. user: «А в 13:00 свободно?»
4. assistant: подтверждает 13:00 (или предлагает ближайшее)
5. → полный flow

_Хард._ `book_appointment.startTime` оканчивается на `13:00:00` во вторник.

### A4 — Смена врача (явное «к Петрову»)
_Цель._ Пациент выбирает конкретного врача из списка.
_Шаги._
1. user: «Запиши к терапевту в субботу»
2. assistant: показывает Петрова (Иванова не работает по субботам)
3. user: «К Петрову беру в 10:00»
4. … flow

_Хард._ `book_appointment.doctorId=1004`, дата = ближайшая суббота.

### A5 — Смена услуги в процессе
_Цель._ Пациент переключается между запросами.
_Шаги._
1. user: «Хочу записаться на ботокс»
2. assistant: предлагает (Беляева/Морозова)
3. user: «Нет, лучше на пилинг»
4. assistant: переключается, предлагает пилинг
5. user: выбирает, flow до записи

_Хард._ Финальный `book_appointment.price=4200` (Дерматологический пилинг), не 11500 (Ботокс).

### A6 — Смена специализации (терапевт → косметолог)
_Цель._ Пациент полностью меняет тип записи.
_Шаги._
1. user: «Запиши к терапевту»
2. assistant: слоты терапевта
3. user: «А вообще передумал, запишите к косметологу»
4. assistant: слоты косметолога
5. → flow

_Хард._ Финальный `specialityId=9` (Косметолог), не 1 (Терапевт).

### A7 — Запрос «А есть подешевле?»
_Цель._ Бот корректно обрабатывает запрос по цене.
_Шаги._
1. user: «Запиши на ботокс»
2. assistant: предлагает (11500 у Беляевой и Морозовой)
3. user: «А подешевле есть варианты?»
4. assistant: предлагает альтернативы (другие услуги) ИЛИ объясняет, что цена одинаковая
5. user: «Тогда возьму у Морозовой» (она дешевле в среднем)
6. … flow

_Софт._ В reply шага 4 либо упоминание цены, либо альтернативные услуги.

## B. Передумывание / отмена в процессе

### B1 — «Нет, передумал» после сводки
_Цель._ Сессия корректно сбрасывается, ничего не записывается.
_Шаги._
1. user: «Запиши к терапевту в пятницу»
2. assistant: слоты
3. user: «Беру в 10:00»
4. assistant: спрашивает данные
5. user: даёт данные
6. assistant: сводка, «Подтверждаете?»
7. user: «Нет, передумал»
8. assistant: соглашается отменить намерение

_Хард._ В истории НЕТ `function:book_appointment.success=true`. `appointments.json` не вырос.
_Софт._ В reply шага 8 — слова «хорошо», «отменим», или подобное.

### B2 — Отказ после ввода данных
_Цель._ Данные не отправляются, если пациент передумал.
_Шаги._
1–4. Аналогично B1
5. user: даёт данные
6. assistant: сводка
7. user: «Стоп, не надо»
8. assistant: останавливает

_Хард._ `book_appointment` либо не вызывался, либо вернул `confirmation_required` — но НЕ `success`.

### B3 — Стоп до выбора слота
_Цель._ Ранний отказ после первого ответа бота.
_Шаги._
1. user: «Запиши к терапевту»
2. assistant: слоты
3. user: «Ладно, потом сам напишу»

_Хард._ Ничего не записано. Сессия живая, но без booking.

## C. Перенос существующей записи

### C1 — Перенос на другой день
_Цель._ Старая запись отменяется, новая создаётся.
_Предусловия._ Уже есть запись (создаётся первым шагом теста или предварительно).
_Шаги._
1. (setup) user: «Запиши к терапевту в среду» → создаёт запись
2. user: «А давай перенесём на пятницу»
3. assistant: показывает слоты пятницы
4. user: «Беру в 10:00»
5. assistant: спрашивает подтверждение переноса (или сводку)
6. user: «Да»
7. assistant: «Перенесена»

_Хард._ В моке: запись на среду → `canceled=true`. Новая запись на пятницу → `canceled=false`, `success=true` от `book_appointment`. Или `reschedule_appointment.success=true`.

### C2 — Перенос на другое время того же дня
_Цель._ Меняем только время.
_Шаги._
1. (setup) запись в среду 10:00
2. user: «Перенеси на 14:00»
3. assistant: подтверждает
4. user: «Да»

_Хард._ Старая на 10:00 отменена, новая на 14:00.

### C3 — Перенос со сменой врача
_Цель._ Запись к Ивановой → перенос к Петрову.
_Предусловия._ Запись к Ивановой в пятницу.
_Шаги._
1. user: «А давай не к Ивановой, а к Петрову»
2. assistant: ищет ближайший слот Петрова
3. user: «На субботу 10:00»
4. assistant: подтверждение
5. user: «Да»

_Хард._ Новая запись с `doctorId=1004` (Петров), старая с `doctorId=1001` отменена.

### C4 — Перенос когда несколько записей — уточнение какой
_Предусловия._ Две записи (пилинг + терапевт).
_Шаги._
1. user: «Перенеси мою запись на другой день»
2. assistant: «У вас две записи, какую?»
3. user: «К терапевту»
4. assistant: даёт варианты дат
5. user: выбирает
6. … flow

_Хард._ Перенесена только запись к терапевту, пилинг не тронут.

### C5 — Отказ от переноса в процессе
_Шаги._
1. (setup) запись существует
2. user: «Перенеси»
3. assistant: спрашивает новый день/время
4. user: «А, ладно, оставлю как есть»

_Хард._ Оригинальная запись не тронута (`canceled=false`).

## D. Отмена записи

### D1 — Отмена единственной записи
_Цель._ Простая отмена без уточнения.
_Шаги._
1. (setup) одна запись
2. user: «Отмени мою запись»
3. assistant: показывает её, спрашивает подтверждение
4. user: «Да»
5. assistant: «Отменена»

_Хард._ В моке запись с `canceled=true`.

### D2 — Отмена при нескольких записях — выбор какой
_Предусловия._ Две записи (терапевт + косметолог).
_Шаги._
1. user: «Отмени запись»
2. assistant: «Какую — к терапевту или к косметологу?»
3. user: «К терапевту»
4. assistant: показывает её, спрашивает подтверждение
5. user: «Да»

_Хард._ Отменена ТА запись (терапевт). Косметолог не тронут.

### D3 — Отмена по упоминанию врача
_Шаги._
1. user: «Отмени запись к Петрову»
2. assistant: находит, подтверждает
3. user: «Да»

_Хард._ Отменена именно запись к Петрову (правильный UUID).

### D4 — Отказ от отмены
_Шаги._
1. user: «Отмени мою запись»
2. assistant: показывает, спрашивает «Да/Нет»
3. user: «Передумал, оставлю»

_Хард._ Запись НЕ отменена.

## E. Конфликтные ситуации

### E1 — Двойная запись на одно время → «заменить»
_Цель._ MedFlex 409 → resolution path «заменить».
_Предусловия._ Запись в среду 10:00 к Ивановой.
_Шаги._
1. user: «Запиши к терапевту в среду 10:00 (опять)»
2. assistant: 409 → «У вас уже есть запись на это время, заменить или выбрать другое?»
3. user: «Заменить»
4. assistant: «Заменено» (старая отменена, новая создана)

_Хард._ Старая uuid → `canceled=true`, новая uuid → `success=true`.

### E2 — Двойная запись → «выбрать другое время»
_Шаги._ Те же 1–2, потом
3. user: «Выберу другое время»
4. assistant: предлагает альтернативы
5. user: выбирает
6. → flow

_Хард._ Старая запись не тронута, новая создана на другое время.

### E3 — Двойная запись → «оставить обе» (local DB only)

## F. Гостевой режим — ввод данных

### F1 — Данные не сразу полностью
_Цель._ Бот переспрашивает недостающие поля.
_Шаги._
1. user: «Запиши на пилинг в среду»
2. assistant: предлагает Беляеву/Морозову
3. user: «Беляеву в 11:00»
4. assistant: спрашивает ФИО/телефон/ДР
5. user: «Иванов Иван»
6. assistant: «Нужно ещё телефон и ДР»
7. user: «+79991234567, 1 января 1990»
8. assistant: сводка, подтверждение
9. user: «Да»

_Хард._ Финальный `book_appointment.success=true`, данные собраны полностью.

### F2 — Кривой телефон → переспрос
_Шаги._
1–4. Как в F1
5. user: «Иванов Иван Иванович, телефон ХХХ-ХХХ, 1990»
6. assistant: «Не могу распознать телефон, уточните»

_Хард._ Финальные args содержат нормализованный `phone=79991234567`.

### F3 — Кривая ДР → переспрос
_Шаги._ Аналогично F2 но с датой рождения. «Я родился очень давно» → бот переспрашивает.

### F4 — Отказ давать данные
_Шаги._
1–4. Как в F1
5. user: «Не хочу давать персональные данные»
6. assistant: объясняет, что это нужно для записи (или останавливается)

_Хард._ Запись не создана.

## H. Долгий диалог с множественными уточнениями

## I. Сложные / расплывчатые формулировки

_Шаги._

_Шаги._

## Реализация

- **Файл:** `cycle3-multi-turn.ts`
- **Тип ассерта:** в основном HARD (поведение бэкенда), SOFT для тональности.
- **Хелперы для добавить в `lib.ts`:**
  - `getLastBookingArgs(history)` — args последнего `book_appointment` (из function_call).
  - `getCanceledUuids(history)` — uuid из `cancel_appointment.success`.
  - `countBookings(history)` — сколько успешных книжингов.
  - `getMockAppointments()` — читает `medflex-mock/data/appointments.json` и возвращает массив (для проверки фактического состояния).
- **`resetMock()`** в начале файла + по группам, где нужно вернуться к чистому состоянию (например, перед группой C — отдельная сессия с предварительной записью).
- **Стоимость:** примерно 6–10 LLM-вызовов на тест × ~30 тестов = ~250 вызовов. ≥600K токенов. Запускать осознанно.

## Приоритеты для первой реализации

Если делать поэтапно:

1. **MVP (~7 тестов):** A1, A2, B1, C1, D1, F1, G1 — покрывают основные многоходовые пути.
2. **+ конфликты:** E1, E2 — важная логика `pendingConflict`.
3. **+ долгие диалоги:** H1, H2 — стресс-тест на состояние сессии.
4. **+ edge cases:** J1, J2 — устойчивость к мусору.
